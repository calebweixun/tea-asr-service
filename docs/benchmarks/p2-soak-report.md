# P2 連續一小時壓力測試報告

執行日期：2026-09-19。狀態：**通過。** docs/05 要求「連續一小時 backlog 不持續成長」。

## 方法

以實際時間循環送同一段 75 秒的真實口語錄音，維持一個 continuous session，
每分鐘記錄延遲、未定稿 backlog 與 RSS：

```bash
uv run python benchmarks/soak_continuous.py --wav <take>.wav --minutes 60
```

延遲量的是 docs/05 定義的「說完到定稿」：以 session 起點的 wall clock 加上
`end_sample` 推算說話結束的時刻，再與 final 到達的時刻相減。
送音訊對絕對時間軸排程，否則每個 frame 睡固定時間會累積漂移，把延遲量成服務從未造成的樣子。

## 結果（M4 Pro、48 GiB）

60 分鐘、3,600 秒音訊、**386 段定稿、0 個錯誤**。

| 指標 | 前 10 分鐘 | 後 10 分鐘 | 目標 |
|---|---:|---:|---|
| 說完到定稿 p50 | 0.458 秒 | 0.454 秒 | — |
| 說完到定稿 p95 | 0.550 秒 | 0.555 秒 | p95 ≤ 2 秒 |
| 未定稿 backlog | 9.95 秒 | 6.51 秒 | 不得持續成長 |
| API 程序 RSS | 140.5 MB | 143.9 MB | — |
| worker RSS | 1,484 MB | 1,504 MB | 峰值 ≤ 4 GiB |

整段期間 p95 最大 0.593 秒，全程沒有一分鐘超過 0.6 秒。

**backlog 不成長：** 每分鐘在 1–27 秒之間震盪並回落，後段平均比前段低。
震盪來自素材本身——那段 9.3 秒的長句在封口前都算未定稿，所以循環到它時 backlog 就會跳一次。

**記憶體不呈階梯成長：** 一小時內 API 程序增加 3.4 MB、worker 增加 19 MB，
之後就在該水位附近平穩震盪，沒有每次循環往上一階的形狀。

## 沒有涵蓋的

- **單一 session、單一語者、循環同一段錄音。** 多路併發、多語者、不同長度的素材都沒測。
- **沒有同時開串流預覽。** 本次是 final-only；預覽的混合負載另見 [P2a 報告](p2a-preview-report.md)，
  但那只跑了 75 秒，不是一小時。
- 沒有測 idle 卸載與長跑交錯的情況（長跑期間模型一直忙，不會觸發閒置卸載）。
- 沒有在低階機器上測。這台的 RTF 約 0.03，餘裕很大，較慢的機器上 backlog 行為可能完全不同。
