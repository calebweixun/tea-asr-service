# P2a 串流預覽驗收報告

執行日期：2026-09-19。狀態：**依 [07](../07-contextual-streaming.md) 的五項條件量測完成，預設改為開啟。**

重跑：

```bash
uv run python benchmarks/preview_eval.py --wav <take>.wav
uv run python benchmarks/mixed_load.py --wav <take>.wav
```

素材為使用者錄的 10 句真實口語（75 秒，M4 Pro、MacBook Pro 內建麥克風），以實際時間送出。

**final 與 final-only 完全一致**是最關鍵的一項：預覽共用同一個 worker，若排程有誤會排擠正式推論而讓定稿變差。實測沒有。

## 文字抖動與錯改對／對改錯

35 次修訂轉換中，18 次更接近定稿、10 次更遠離、7 次不變。

但這個「更遠離」的數字**被高估了**：指標是「partial 的前綴有多少比例存活到 final」，
所以每次新增還沒被後文確認的字都會讓比例下降，即使既有文字完全沒被改壞。典型的良性成長：

```text
rev1: 我要查的。
rev2: 我要查的是資訊。
rev3: 我要查的是資訊，不是知識。
```

真正的「對改錯」有實際案例，而且方向與預期相反——**是定稿把預覽改壞的**：

```text
rev4: 請幫我轉接給陳建宏經理，還有林佳蓉。      ← 正確
rev5: 請幫我轉接給陳建宏經理，還有林佳蓉小姐。  ← 正確
final: 請幫我轉接給陳建宏經理，還有林嘉蓉小姐。  ← 佳→嘉，變錯
```

同一段音訊多給後文反而讓人名認錯。這不是預覽機制的缺陷，是模型在較長輸入下的行為，
但它說明「final 一定比 partial 好」並不成立。final 仍然是唯一可注入文件的版本
（契約要求終局不可改），使用者看到的仍是正確流程。

## 決定

`partial_transcripts` 與 `protocol_version=1.1` 改為**預設開啟**。要關掉：

```bash
TEA_ASR_REVISABLE_PREVIEW=0 uv run tea-asr serve
```

或在 `config.toml` 寫 `revisable_preview = false`。關閉時 revisable 請求回 `unsupported_option`，
不會靜默降級成 final-only。

## 這份驗收沒有涵蓋的

- **只有一位語者、一支麥克風、一次 75 秒錄音。** 多語者、遠場、吵雜環境都沒測。
- **`preview.status paused` 的降級路徑沒有被實際觸發**，因為這台機器太快。程式路徑有單元測試覆蓋，
  但沒有在真實過載下驗證過。低階機器上的行為未知。
- 同音詞只有一個案例（「姿勢」被認成「知識」，預覽與定稿都錯），樣本太少。
- 長時間會議下的預覽成本沒有單獨量測。
